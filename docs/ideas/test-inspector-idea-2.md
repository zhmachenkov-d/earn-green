Смотри, ключевая мысль: **тест валиден не тогда, когда он зелёный, а тогда, когда он умеет падать по правильной причине**. Если сломать поведение, тест должен упасть. Если поведение корректно — пройти. Всё остальное вторично.

## Почему AI-тесты часто дают «зелёную пустоту»

Типичные проблемы AI-сгенерированных тестов:

1. **Генерируются от реализации, а не от спеки.** AI видит код и закрепляет текущее поведение, включая баги.
2. **Слабые assertions.** `assert result is not None`, `assertTrue(True)`, проверка только факта отсутствия исключения.
3. **Over-mocking.** Тестируются моки, а не реальное поведение. Интеграционные баги не ловятся.
4. **Покрытие строками без проверки смысла.** Код выполнился — coverage вырос, но что именно проверено — непонятно.
5. **Нет границ и негативных сценариев.** Только happy path.
6. **Текущий вывод как оракул.** AI просто записал то, что вернул код, а не то, что должно быть по требованиям.
7. **Недетерминизм.** Время, random, сеть, порядок тестов.

## Критерий валидности теста

Тест `T` для кода `C` и спеки `S` валиден, если:

- он проверяет `S`, а не детали реализации;
- он падает хотя бы на одной мутации `C`, которая нарушает `S`;
- он проходит на корректном `C`;
- он детерминирован и изолирован;
- при падении понятно, что именно сломалось.

Это ровно то, что автоматически проверяет **mutation testing**.

## Как проверять AI-тесты: практический контур

1. **Traceability до требований.**
   У каждого теста должна быть ссылка на acceptance criteria, инвариант или сценарий. Нет требования — AI его выдумает.

2. **Mutation testing — главный инструмент.**
   Берём изменённые файлы, запускаем мутантов: `>`, `<`, `+`, `-`, удаление вызова, замена константы. Если мутант выжил — тест не проверяет это место. Инструменты: `mutmut`, `Stryker`, `PIT`, `cargo-mutants`. В CI ставим порог по mutation score для diff.

3. **Test-the-tests / negative controls.**
   Вручную или автоматически ломаем код и смотрим, падают ли тесты. Если нет — тест бесполезен.

4. **Независимые оракулы.**
   - спека/контракт;
   - reference implementation;
   - metamorphic relations: «сортировка — это перестановка и порядок»;
   - differential testing: новая версия vs старая;
   - property-based testing: `Hypothesis`, `fast-check`, `jqwik`;
   - fuzzing для парсеров и валидаторов.

5. **Adversarial AI-агент.**
   Один агент пишет тесты, другой — пытается их сломать: генерирует мутантов, ищет слабые assertions, over-mocking, пропущенные границы. Это дешевле, чем человек, и хорошо масштабируется.

6. **Ревью по чеклисту.**
   - Есть ссылка на требование?
   - Если сломать код, тест упадёт?
   - Проверяет результат, состояние, ошибку, побочные эффекты?
   - Есть границы, пустые, null, невалидные, конкурентные кейсы?
   - Моки только на внешних границах?
   - Детерминирован?
   - Не тестирует приватные методы и реализацию?
   - Понятно ли сообщение при падении?

## Как решить проблему зелёных тестов и неполного покрытия

Покрытие строками — необходимое, но недостаточное. Нужны метрики, которые измеряют **качество проверки**:

- **Line/branch coverage** — базово.
- **Diff coverage** — покрытие нового/изменённого кода. Гейт: например, 90% для diff.
- **Mutation score** — главная метрика валидности тестов.
- **Requirement coverage** — сколько acceptance criteria реально покрыто.
- **Flaky rate** — доля нестабильных тестов.
- **Escaped defects** — сколько багов ушло в прод. Это финальная правда.

CI-гейты:

- diff coverage ниже порога — блок;
- mutation score по изменённым файлам ниже порога — блок;
- новые test smells — блок;
- новый flaky-тест — quarantine, не merge;
- нет ссылки на требование для P0/P1 — блок.

Промпт для AI-агента должен быть не «сгенерируй тесты», а:

> Сгенерируй тесты от спеки, не от реализации. Для каждого теста укажи требование. Покрой happy path, границы, невалидные входы, ошибки, побочные эффекты. Не используй implementation details. Не делай over-mocking. Добавь property-based тесты и мутационные проверки.

## Пример

Плохо:

```python
def test_transfer():
    assert transfer(a, b, 100) is not None
```

Хорошо:

```python
def test_transfer_moves_money():
    a = Account(100)
    b = Account(0)
    transfer(a, b, 30)
    assert a.balance == 70
    assert b.balance == 30

def test_transfer_insufficient_funds():
    with pytest.raises(InsufficientFunds):
        transfer(Account(10), Account(0), 30)
```

Если в коде заменить `-` на `+`, хороший тест упадёт, плохой — останется зелёным.

## Итог

Валидность AI-тестов проверяется не глазами, а **мутациями, независимыми оракулами и adversarial-ревью**. Зелёные тесты без mutation score — это самообман. Полное покрытие — это покрытие требований и мутаций, а не строк. Если AI-агент оптимизирует «чтобы тесты прошли», он будет скрывать баги. Его цель должна быть «найти баг», а не «получить зелёный CI».
